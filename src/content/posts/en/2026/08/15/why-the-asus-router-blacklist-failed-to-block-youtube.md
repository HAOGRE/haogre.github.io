My ASUS router runs Xray with FakeDNS. One day, I added the bedroom Apple TV to the router’s blacklist and got a puzzling result: Chinese websites and video services stopped working, but YouTube continued playing normally.

Before installing the proxy, the ASUS blacklist could cut off a device’s internet access completely. Afterward, it blocked only half the traffic. YouTube was not doing anything special. The same device’s traffic was simply taking two different paths through the kernel.

![The blacklist stops domestic traffic while YouTube slips through a side channel](/uploads/2026/08/15/华硕路由器黑名单为什么拦不住YouTube/01-blacklist-paradox.png)

<small>Figure 01 | The blacklist works, but it guards only one of the two doors</small>

This post documents the investigation and the eventual fix. The router runs ASUSWRT-koolcenter-mod, and the LAN is `192.168.100.0/24`. Xray uses FakeDNS to map domains that need proxying into `198.18.0.0/16`, then redirects their TCP traffic to local port `12345`.

## The behavior makes sense once you see the two paths

The ASUS blacklist is enforced by the `PControls` chain. When a device visits an ordinary website, its packets enter the router from the LAN, pass through `filter/FORWARD`, and are dropped when they match the rule for the device’s MAC address.

```text
LAN device
  → filter/FORWARD
  → PControls
  → DROP
```

FakeDNS traffic takes a different route. For domains such as YouTube, Xray returns fake IP addresses within `198.18.0.0/16`. A NAT rule on the router then redirects TCP traffic for that range to local port `12345`:

```sh
iptables -t nat -A PREROUTING \
  -p tcp -d 198.18.0.0/16 \
  -j REDIRECT --to-ports 12345
```

After `REDIRECT`, the packet’s destination is the router itself. Instead of passing through `FORWARD`, it enters `INPUT` and is handed to Xray, which is listening on port `12345`.

![Network topology before the fix](/uploads/2026/08/15/华硕路由器黑名单为什么拦不住YouTube/02-broken-topology.png)

<small>Figure 02 | Ordinary traffic passes through FORWARD, while FakeDNS traffic enters Xray through INPUT</small>

The complete paths look like this:

```text
Ordinary domestic traffic
ATV → br0 → FORWARD → PControls → DROP

FakeDNS proxy traffic
ATV → br0 → nat/PREROUTING → REDIRECT :12345
    → INPUT → Xray → proxy node → YouTube
```

The blacklist never stopped working. It was still doing its job on `FORWARD`; it simply never saw the proxy traffic entering through `INPUT`.

## Confirming the root cause from the live system

First, I inspected the filter rules generated by ASUSWRT:

```sh
iptables-save -t filter | grep -E 'FORWARD|PControls'
```

After blacklisting a test phone, I saw rules like these:

```text
-A FORWARD -i br0 -m mac --mac-source XX:XX:XX:XX:XX:XX -j PControls
-A PControls -i br0 -m mac --mac-source XX:XX:XX:XX:XX:XX -j DROP
```

The counters showed that 80 packets hit `PControls` and were dropped when the phone accessed ordinary addresses. That matched the failure of domestic sites and services.

Next, I checked the NAT rule and listening port:

```sh
iptables-save -t nat | grep -E '198\.18\.0\.0/16|12345'
netstat -lntp | grep ':12345'
```

The router had both of the critical pieces in place:

```text
-A PREROUTING -d 198.18.0.0/16 -p tcp -j REDIRECT --to-ports 12345
tcp  0  0  :::12345  :::*  LISTEN  xray
```

Finally, I inspected connection tracking:

```sh
conntrack -L | grep 'src=192.168.100.243' | grep 'dst=198.18.'
```

Although the test phone was already on the ASUS blacklist, it still had several connections to `198.18.x.x:443`. The reply tuples showed that those connections had been taken over by `192.168.100.1:12345`, and one had already transferred nearly 1 MB. YouTube playback was not cached or imagined. The traffic really was reaching Xray.

![PControls guards FORWARD while proxy traffic enters through INPUT](/uploads/2026/08/15/华硕路由器黑名单为什么拦不住YouTube/03-two-doors.png)

<small>Figure 03 | The blacklist guards FORWARD, but Xray’s entrance is on INPUT</small>

The root cause in one sentence: **the ASUS blacklist exists only on `FORWARD`, while the FakeDNS transparent proxy redirects overseas traffic to the router’s local `INPUT:12345`.**

## Why not jump directly to PControls?

The most obvious fix is to add a rule at the top of `INPUT`:

```sh
iptables -I INPUT 1 -i br0 -p tcp --dport 12345 -j PControls
```

On this router, the kernel rejected the command with `iptables: Invalid argument`. The reason was that `PControls` contained more than MAC-based drop rules. It also included a `TCPMSS` target intended for forwarded traffic:

```text
-A PControls -p tcp --tcp-flags SYN,RST SYN \
  -j TCPMSS --clamp-mss-to-pmtu
```

`TCPMSS` was valid on the existing forwarding path, but the entire chain could not be called directly from the `INPUT` hook. Reusing `PControls` wholesale was therefore not an option.

Another approach would be to hard-code the Apple TV’s or phone’s MAC address:

```sh
iptables -I INPUT 1 -i br0 -p tcp --dport 12345 \
  -m mac --mac-source XX:XX:XX:XX:XX:XX -j DROP
```

That works, but it creates a second blacklist. Removing a device in the ASUS interface would leave the old rule behind, and an iPhone could stop matching after its private Wi-Fi address changed. The maintenance cost was too high.

## The final approach: copy the MAC drops, not the whole chain

The solution was to create an in-memory chain named `XRAY_PCONTROLS`. Whenever ASUSWRT rebuilds the firewall, the script extracts the current MAC `DROP` entries from `PControls`. Traffic arriving at `INPUT:12345` then jumps to this clean chain.

I placed the following block in `/jffs/scripts/firewall-start`, before the existing Xray NAT rules:

```sh
#!/bin/sh

# Make Xray FakeDNS traffic obey the Asus parental-control blacklist.
# PControls also contains TCPMSS, which cannot be called from INPUT, so copy
# only its MAC DROP entries into a runtime-only chain.
if iptables -nL PControls >/dev/null 2>&1; then
    iptables -N XRAY_PCONTROLS 2>/dev/null || true
    iptables -F XRAY_PCONTROLS

    for blocked_mac in $(
        iptables-save -t filter |
        sed -n 's/^-A PControls .*--mac-source \([^ ]*\) -j DROP$/\1/p'
    ); do
        iptables -A XRAY_PCONTROLS \
          -i br0 -m mac --mac-source "$blocked_mac" -j DROP
    done

    iptables -C INPUT -i br0 -p tcp --dport 12345 \
      -j XRAY_PCONTROLS 2>/dev/null ||
    iptables -I INPUT 1 -i br0 -p tcp --dport 12345 \
      -j XRAY_PCONTROLS
else
    # Fail open: do not keep stale MAC entries.
    iptables -F XRAY_PCONTROLS 2>/dev/null || true
    logger -t firewall-start \
      "PControls chain unavailable; Xray blacklist guard left empty"
fi
```

Several boundaries in this script are deliberate.

`XRAY_PCONTROLS` exists only in runtime memory and does not persist any MAC addresses. The ASUS blacklist remains the single source of truth. Whenever a device is added or removed in the interface, the next firewall rebuild copies the current rules again.

The script guards only Xray’s TCP entry point on port `12345`. It does not cut off DNS, DHCP, the router’s administration interface, or communication between devices on the same subnet. A blacklisted Apple TV can still reach a local NAS, but it cannot use Xray to reach the internet.

If `PControls` has not been created at startup, the script flushes the old runtime chain and allows traffic instead of retaining stale MAC entries. A sudden power loss therefore cannot leave behind a permanent blacklist that cannot be cleared from the ASUS interface.

The jump rule is checked with `-C` before insertion. Running `firewall-start` repeatedly will not keep adding duplicate jumps to `INPUT`.

After the fix, the paths look like this:

```text
Ordinary internet traffic
LAN → FORWARD → PControls → DROP

FakeDNS proxy traffic
LAN → PREROUTING → INPUT:12345 → XRAY_PCONTROLS → DROP

Local network traffic
ATV → br0 → NAS
```

## Deploying safely

`firewall-start` lives on JFFS. Overwriting it directly could leave a partial file if the router lost power at the wrong moment, so I first kept a copy of the original script:

```sh
cp -p /jffs/scripts/firewall-start \
  /jffs/scripts/firewall-start.pre-xray-pcontrols
```

I wrote the new script to a temporary file in the same directory, checked it with `sh -n`, set its permissions, and ran `sync`. I then replaced the original atomically with `mv`, checked the syntax again, and executed the script once to load the rules.

```sh
sh -n /jffs/scripts/.firewall-start.new
chmod 755 /jffs/scripts/.firewall-start.new
sync
mv /jffs/scripts/.firewall-start.new /jffs/scripts/firewall-start
sync
sh -n /jffs/scripts/firewall-start
/jffs/scripts/firewall-start
```

This process protects the startup script itself. Whether a device belongs on the blacklist is still managed by ASUSWRT’s NVRAM state and `PControls`.

## Verification

I did not verify the fix by checking YouTube alone. I tested blacklisted and unlisted devices, local network access, and repeated firewall reloads.

### 1. The guard rule appears only once

I ran `firewall-start` twice and counted the matching jump rules:

```sh
iptables-save -t filter |
  grep -c -- '-A INPUT .*--dport 12345 -j XRAY_PCONTROLS'
```

The result was `1`, confirming that the script was idempotent.

### 2. A blacklisted device hits the proxy drop rule

After blacklisting the test phone and refreshing YouTube, the counters on `INPUT` and `XRAY_PCONTROLS` began to increase:

```sh
iptables -t filter -nvL INPUT --line-numbers |
  grep XRAY_PCONTROLS

iptables -t filter -nvL XRAY_PCONTROLS --line-numbers
```

The MAC-specific `DROP` rule for the phone gained a packet, while its number of established proxy connections fell to `0`:

```sh
conntrack -L |
  grep 'src=192.168.100.243 .*dst=198.18.' |
  grep -c ESTABLISHED
```

### 3. Proxy access still works for unlisted devices

At the same time, other devices still had 74 established connections to `198.18.0.0/16`. The Xray process and the listener on port `12345` were both healthy. The new rule dropped only blacklisted MAC addresses; it did not alter Xray’s routing, proxy node, DNS, or encryption path.

### 4. Access returns automatically after removing a device

After I removed the test phone from the ASUS interface, both `PControls` and `XRAY_PCONTROLS` went from four MAC entries back to three. Established connections from the phone to `198.18.x.x` reappeared without restarting Xray or deleting firewall rules manually.

### 5. Local network access remains available

Traffic from the blacklisted device to a NAS on the same subnet never enters `INPUT:12345`. The fix adds no blanket drop rule for all of `br0` or `INPUT`, so local communication remains available while both direct and proxied paths to the internet are blocked.

## Where this fix applies, and where it does not

This setup uses IPv4 FakeDNS with NAT `REDIRECT`, so guarding TCP port `12345` on `INPUT` covers the actual bypass path. A future move to TPROXY, TUN, IPv6, or additional transparent-proxy ports would require another inspection of `mangle`, `ip rule`, `ip6tables`, and the listening ports. This rule should not be copied mechanically into a different setup.

When investigating this kind of failure, start with one simple question: do the traffic that access control blocks and the traffic that slips through ultimately pass through the same Netfilter hook? Once a proxy diverts traffic away from the forwarding path and into the router itself, guarding `FORWARD` alone is no longer enough.
