前一阵看到不少讨论，说 Agent 已经会用命令行，MCP 又绕又重，直接给它 CLI 就好了。最近又感觉 MCP 的声音多了起来，于是冒出一个疑问：CLI 和 MCP 到底差在哪里，为什么大家的偏好像钟摆一样来回摆？

我没有一份足以证明“CLI 降温、MCP 回升”的采用率数据。信息流里的热度也会受关注对象影响。但这个疑问值得往下追，因为两边的理由经常都成立：命令行确实好用，统一接入也确实有价值。

如果只写一句“CLI 适合开发者，MCP 适合平台”，解释得还是太浅。我试着连续追问五次，看看分歧最后落在哪里。

## 第一次追问：既然都能调用工具，为什么还会争？

CLI 是命令行接口。程序接受参数、读取输入，通过标准输出、标准错误和退出码返回结果。一个 Agent 可以像脚本一样使用它。

比如，在已经安装并登录 GitHub CLI 的环境里，下面这条命令可以读取一条 issue 的标题和正文：

```bash
gh issue view 123 --repo owner/repo --json title,body
```

这里的仓库和编号只是示例。[GitHub CLI 的文档](https://cli.github.com/manual/gh_issue_view)明确提供了 `--json` 和 `--jq` 选项，CLI 并不只能输出给人看的终端文本。

MCP，即 Model Context Protocol，是 AI 应用与外部能力之间的通信协议。宿主应用管理 MCP 客户端，客户端连接服务端，发现工具，再按约定的消息格式调用它们。[MCP 的架构文档](https://modelcontextprotocol.io/specification/2025-06-18/architecture)还包括资源和提示模板等能力，本文只讨论经常被拿来与 CLI 比较的工具调用。

两者的交集是“让 Agent 使用一个能力”，各自标准化的范围却不同：CLI 借用操作系统的进程和输入输出约定，每个程序继续定义自己的命令；MCP 进一步约定能力发现、参数描述和调用消息。具体业务的含义，仍然要由工具作者定义。

| 要处理的事情   | 走 CLI                         | 走 MCP                           |
| -------------- | ------------------------------ | -------------------------------- |
| 知道有哪些操作 | 查帮助、文档或配套 Skill       | 通过协议发现工具及其描述         |
| 知道参数怎么传 | 理解该程序的命令和选项         | 读取工具声明的输入 schema        |
| 组合多步操作   | 使用 Shell 或其他脚本          | 由宿主、Agent 或代码执行层组合   |
| 管理执行环境   | 安装程序，处理版本、依赖和凭据 | 维护客户端、服务端及其连接和授权 |

MCP 可以连接本地进程，CLI 也能访问远程服务。因此，“本地对云端”“文本对 JSON”都不是可靠的分界。

争论之所以出现，是因为在一个具体任务里，它们确实可能提供两条可替代的路径。但 CLI 和 MCP 本身都不保证业务操作正确、权限足够细，或者结果适合交给模型。

## 第二次追问：为什么开发者很容易觉得 CLI 更划算？

因为开发者手里往往已经有一套能用的环境。

Git 装好了，云平台登录过了，测试命令写进了项目，遇到错误知道去哪里看日志。Agent 接过终端，就能利用这些现成投入。再做一个 MCP 服务，如果只是把已有命令包一层，确实可能多出维护工作。

CLI 还有很强的组合能力。假设要找出一个目录里最近失败的任务，脚本可以读取文件、过滤、排序、聚合，只把最后几条结果返回给模型。没有必要让模型逐个读取每份日志，再用自然语言充当循环和条件判断。

这也是我认可 CLI 路线的地方：很多确定性的工作，交给程序执行更直接。模型负责决定查什么、怎样组合，执行环境负责搬运和处理数据。

但这里藏着一笔容易忘记的账。环境已经准备好，不代表准备环境没有成本。只是这笔钱和时间早就由开发者付过了。

把同一套流程交给一个没有终端经验的同事，或者交给几百个身份、权限和设备都不同的用户，安装、登录、升级、故障诊断就会重新出现。平台当然可以预装 CLI、管理容器和凭据；做到这一步，它也在建设一套接入基础设施。

**在现成的开发环境里，CLI 的新增成本很低。把这个结论推广到所有用户，容易把已经付过的成本当成不存在。**

## 第三次追问：MCP 能否把这些成本消掉？

也不能。它能统一一部分接入约定，让一些适配工作由工具提供方和 AI 应用共同承担。

一个服务要接入多个 AI 客户端时，共同协议就有价值。工具提供方不必为每种宿主重新发明完整的发现和调用方式；客户端也可以用共同的机制识别工具、传递参数、处理结果。真实接入仍然需要兼容性测试、权限配置和产品适配，不能把“实现了 MCP”理解成“在所有客户端都能无差别工作”。

这笔账可以粗略记成：

```text
使用工具的总成本
= 接口适配 + 环境运维 + 模型调用 + 权限治理 + 出错后的恢复
```

这不是用来代入数字的定律，而是一张防止漏项的账单。个人开发者可能最在意模型调用和脚本效率，平台可能更在意新增一个服务要做多少适配，企业则会追问谁能访问、离职后如何撤权、操作失败后怎样追溯。

MCP 为其中一些事情提供了协议基础，但没有替企业完成治理。比如，[2025-06-18 版授权规范](https://modelcontextprotocol.io/specification/2025-06-18/basic/authorization)定义的是基于 HTTP 传输的授权流程；授权本身是可选能力，本地 STDIO 场景另有凭据获取方式。不能因为工具挂上了 MCP，就默认它有完善的审计、审批和最小权限。

反过来，CLI 也可以接入 OAuth，可以被沙箱约束，可以记录审计日志。安全差异要看实际授予的权限、执行隔离和服务端校验，不能仅凭接口名称判断。

追问到这里，我更愿意把 MCP 的价值理解成：**把可以重复使用的接入约定做成公共协议，减少每个使用方各自补一遍的工作。** 减少了多少，取决于工具数量、用户数量，以及原来那套环境有多成熟。

## 第四次追问：如果 CLI 更省 token，为什么还要回头考虑 MCP？

“CLI 省 token”经常把几件事混在一起：按需查帮助、用脚本做循环、在执行环境过滤数据，以及只给模型返回摘要。这些做法很有用，但它们并不专属于命令行。

Anthropic 在 2025 年 11 月 4 日发布的 [Code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp) 就讨论了同一个问题：把全部工具定义塞进上下文，再让每一步中间结果都经过模型，会增加成本。文中提出把 MCP 工具呈现为代码接口，让 Agent 按需发现工具，并在执行环境处理数据。

这个例子对我的判断影响很大。MCP 可以负责连接服务，代码负责循环、过滤和拼接，模型只看最后需要判断的部分。CLI 擅长的组合方式，可以与 MCP 的接入机制同时存在。

当然，代码执行层也要维护沙箱、资源限制和状态，复杂度不会凭空消失。对于只有一个工具、一次查询的任务，增加编排层也未必划算。那篇文章里的节省比例来自具体示例，不能直接当成任何系统都会得到的收益。

所以，比较时至少要固定任务、模型、权限和返回数据量，再看成功率、耗时、上下文消耗，以及失败后的恢复成本。拿“每一步都经过模型的 MCP”去比“精心编排的 CLI 脚本”，实际上同时改变了协议和执行方式，很难把结果归因给 MCP。

如果最近确实有人重新重视 MCP，一个可成立的解释是：早期实现带来的代价在被拆开处理，协议的接入价值因此更容易显现。这个解释有技术依据，但仍不能单独证明整个市场正在转向。

## 第五次追问：当执行效率不再构成绝对分界，大家还在争什么？

再往下看，是谁维护入口，谁承担长期支持，谁能决定工具怎样被用户发现和使用。

对开发者来说，CLI 的自主性很有吸引力。只要拿得到程序、文档和合法凭据，就能组合自己的流程，保存脚本，也能替换其中一个环节。工具提供方未必需要为每一种新组合专门设计产品界面。

对平台来说，共同协议则有利于汇集外部能力，再围绕它做连接管理、工具发现、授权界面和统一体验。服务提供方也有理由希望一次集成能触达更多客户端。

这些是我对参与者动机的分析，不代表每个平台都怀着相同目的。开放协议确实能降低迁移门槛；不过，协议可移植不等于整套工作流可移植。如果审批规则、用户授权、状态记录和工具分发都留在一个宿主里，换平台仍然可能很难。

我会因此多问一句：工具定义能搬走以后，用户积累的流程、授权关系和执行记录能不能一起搬走？这比“支持 MCP”这个标签更能说明迁移成本。

对于“势头又回来了”的体感，我现在有一个工作假设：随着讨论对象从个人编程环境扩展到多用户的 AI 产品，承担成本的人变了，评价接口的标准也跟着变了。要验证它，需要观察真实的活跃集成、重复使用和维护投入，不能只数支持声明、服务器目录或社交媒体帖子。

## 协议统一之后，最难的一部分还在

沿着这五次追问，我也遇到了一个反例：就算给工具补上完整 schema，再换成 MCP，它也可能仍然很难用。

比如，做一个“给客户退款”的工具。参数有订单号、金额和原因，类型都正确，只能说明这次请求的形状正确。它没有回答：订单是否已经退款，金额能否超过实付，当前用户是否有权操作，超时后重试会不会退两次。

这些约束要由业务实现落实。幂等键、状态校验、权限检查、可追溯的操作编号、需要审批时的明确状态，都不会因为换了一种接口自动出现。

CLI 也有同样的问题。一个支持 JSON 的命令，如果失败时只返回“操作失败”，成功时又混入进度日志，Agent 一样难以可靠处理。一个 MCP 工具如果叫 `execute`，允许塞入任意命令和万能参数，也可能把刚刚描述清楚的边界重新抹掉。

**我的观点是：判断一个工具是否适合 Agent，优先看它有没有明确的业务边界、可校验的结果和失败后的恢复路径。CLI 与 MCP 决定这些能力怎样被接入，工具本身决定事情能否可靠地做成。**

如果今天让我设计一个内部工具，我会先做好底层业务能力：输入输出稳定，错误能区分，写入有必要的校验和重复执行保护。已有成熟 CLI、主要用户又是研发，就继续把 CLI 做好；需要进入多个 AI 产品、服务更多非研发用户时，再提供 MCP 接口。两边共用业务实现，避免两套入口各自长出一套退款规则。

我也不会因为模型越来越会读文档，就认定接口契约没用了。模型可以更快理解某个工具怎么调用，系统仍然需要确定地检查它有没有权调用、这次操作做了什么、出错后能不能重试。

下次再看到“CLI 赢了”或者“MCP 回来了”，我会先找那张没有被展示的账单：安装和运维算在谁头上，身份和权限由谁负责，中间数据经过哪里，失败由谁处理。如果这些条件没说清楚，所谓胜负很可能只是不同的人在计算不同的成本。
