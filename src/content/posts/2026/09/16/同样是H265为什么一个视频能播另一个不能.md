网页里的一个视频播放不了。播放器没有给出有用的提示，只留下一句“无法播放”。

我让 AI 检查文件，它用 ffprobe 读出了 H.265 / HEVC 编码，于是给出一个很常见的猜测：浏览器的 HEVC 兼容性有问题，可以转成 H.264 试试。

这个解释听起来合理。直到我拿出另一段能播放的视频，检查结果同样是 H.265。

“都是同一个编码，为什么一个能播，一个不能？”这句追问，把排查从经验判断推到了实际验证。

## 编码相同，只是对比的起点

为了方便说明，把不能播放的文件叫作 A，能播放的文件叫作 B。原始链接、文件名、业务信息和画面都不在这里公开。

| 检查项       | 视频 A                          | 视频 B            |
| ------------ | ------------------------------- | ----------------- |
| 封装         | MP4                             | MP4               |
| 视频编码     | HEVC Main，`hvc1`               | HEVC Main，`hvc1` |
| 音频编码     | AAC-LC                          | AAC-LC            |
| 额外数据轨道 | `mebx`，名称为 `timed_metadata` | 无                |
| 索引位置     | 文件末尾                        | 文件前部          |
| 原页面表现   | 无法播放                        | 可以加载          |

两个文件的分辨率、码率和体积也不同。不过，“存在差异”和“差异导致故障”是两件事，列完参数不能直接把其中一项当作原因。

AI 接着用 FFmpeg 完整解码了两段文件，都没有报解码错误。这说明当前版本的 FFmpeg 能处理它们，但还不能据此保证浏览器也能播放。两者采用的解析器、解码器和配置可能不同。

## 浏览器卡在了读取文件结构这一步

我们在本机搭了一个临时对照页，让同一个浏览器读取下载后的两个文件，并把播放器的错误状态显示出来。A 仍然失败，B 正常加载。

这次拿到了明确报错：

```text
PipelineStatus::DEMUXER_ERROR_COULD_NOT_OPEN:
FFmpegDemuxer: open context failed
```

Demuxer 是解封装器。播放 MP4 时，浏览器需要先读懂文件的轨道、时间信息和样本位置，取出音视频数据，再交给解码器。

这条错误把范围缩到了文件解析阶段。继续围绕“是不是不支持 H.265”打转，已经无法解释当前证据。

## 重新封装能加载，还需要再缩小范围

AI 先保留 A 的视频和音频轨道，用 `-c copy` 无损重新封装，并把索引移到文件前部。处理后，浏览器能读到视频尺寸和时长，状态也变成了可播放。

这是个有用的结果，但这次操作同时改变了几件事：额外轨道被去掉，封装信息被重写，索引位置也变了。此时只能说“重新封装有效”，还不能确定是哪一项起作用。

于是又做了两个对照：

| 实验                         | 改动                                     | 结果                  |
| ---------------------------- | ---------------------------------------- | --------------------- |
| 无损重新封装，索引仍放在末尾 | 保留音视频，重写封装                     | 正常加载              |
| 原文件仅忽略额外元数据轨道   | 音视频数据、文件长度、索引位置均保持不变 | 实际播放进度超过 7 秒 |

第二个实验最有说服力。它只在测试副本中把那条元数据轨道的外层 `trak` 标记改为可跳过的 `free`，没有重新编码，也没有移动原来的音视频数据。

这一步把故障定位到了 A 中那条 `mebx` 元数据轨道与当前浏览器解析器之间的兼容性问题。更细的内部字段为什么触发失败，还没有继续追到解析器源码，不能把它扩大成“所有 mebx 都不兼容”。

## mebx 从哪里来

MP4 可以包含画面、声音之外的轨道。`mebx` 用于盒装元数据样本，可以承载随时间变化的附加信息。录制或导出软件可能把这些信息一起写进文件。

A 的文件元信息带有录制软件标记，额外轨道的名称是 `timed_metadata`。这支持“它在录制或导出环节被写入”的推测，但我们没有解析具体载荷，不能断言里面保存了哪一种传感器或画面处理数据。

对这次网页播放而言，忽略这条轨道以后，原有的画面和声音就能继续被读取。

## 这个案例的处理方式

对只需要一条主视频和一条主音轨的普通播放副本，可以这样重新封装：

```bash
ffmpeg -n -i input.mp4 \
  -map 0:v:0 -map '0:a:0?' \
  -c copy -movflags +faststart output.mp4
```

`-map` 只选择第一条视频轨道和可选的第一条音轨，`-c copy` 直接复制编码后的数据，不重新压缩画面和声音。`+faststart` 把索引移到文件前部，方便网页渐进加载；它不是这次故障的已确认根因。

原文件应当保留。这个命令会舍弃未选中的轨道，如果文件还需要多语言音轨、字幕或专业元数据，就要按用途调整，不能直接用于替换归档原件。输出文件仍需在目标浏览器里检查播放、拖动和音画同步。

这次让我觉得 AI 很强的一点，是它能连续完成文件分析、浏览器检查、对照实验和修复副本制作。我只需要补上“另一段同样编码却能播放”这个反例，它就能沿着新证据继续查。一个原本可能被“转码试试”带过去的问题，最后有了可以复核的原因和更小的处理方式。
