家里的网络已经出现过几次相似的故障：光猫看起来正常，路由器后台却显示没有互联网，所有设备都无法访问外网。拔插一次光猫与路由器之间的网线，或者重启路由器，网络就会恢复。

拔线和重启都能解决眼前的问题，但它们会同时清空 PPPoE 会话、路由、NAT 和策略规则，也会破坏最有价值的故障现场。真正的问题不是“怎样更快地重启”，而是两件事：路由器为什么没有自行恢复，以及怎样在下次自动恢复前留下足够的证据。

这次排查最终把问题收敛到一个更具体的方向：PPPoE 曾经异常断开，随后只完成了认证层面的重连，却没有证据表明 WAN 数据面也得到了完整恢复；与此同时，PPP 保活、网络看门狗和 DNS 探测全部关闭。路由器很可能进入了“会话看似存在，实际流量不通”的状态。

## 先把日志事实和现场观察分开

排障时最容易犯的错误，是把时间上相近的两个事件直接连成因果关系。

系统日志记录了下面这段时间线：

```text
20:47:28  pppd: Modem hangup
20:47:28  pppd: Connection terminated
20:47:30  WAN: Failed to authenticate ourselves to peer
20:47:38  pppd: Connected via WAN interface
20:47:39  pppd: CHAP authentication succeeded
20:47:39  pppd: 获得 IP、PPP 对端和 DNS

21:28:55  HTTPD: Web login succeeded（局域网管理设备）
21:30:54  WAN Ethernet: Link is Down
21:30:56  WAN Ethernet: Link is Up at 1 Gbps
21:31:07  WAN Ethernet: Link is Up at 2.5 Gbps
21:31:14  WAN: restored
```

最初看到 21:30 之后连续出现 `Link is Down` 和速率重新协商，很容易把问题归因于光猫、网线或 2.5G 网口抖动。但现场情况是：21:30 之后的物理掉线来自我手动拔插网线。我是在网络已经不可用、登录路由器确认状态之后，才开始处理。

因此，21:30 的网口日志记录的是恢复动作，而不是原始故障。路由器后台当时显示“没有互联网”，则属于现场观察；日志可以确认 21:28:55 登录过后台，却无法还原网页当时显示的每个字段。只有把这两类证据分开，才能避免将人为操作误判为根因。

## CHAP 成功不等于互联网已经恢复

20:47:39 的 `CHAP authentication succeeded` 只说明用户名、密码和 PPPoE 接入认证成功。它不能证明以下环节全部正常：

- PPP 数据报文能够持续通过运营商接入设备；
- 默认路由已经指向新的 PPP 会话；
- NAT 和连接跟踪状态已经正确更新；
- 自定义策略路由和透明代理规则已经重新加载；
- DNS 请求能够正常到达上游服务器。

这台路由器还运行着 Xray 和自定义防火墙规则。正常、完整的 WAN 启动会依次触发 `wan-start`、`nat-start`、`firewall-start` 和多路由更新。但在 20:47 的重新认证之后，日志里没有出现这些恢复动作，也没有出现 `WAN was restored`。

人工拔插网线之后则完全不同：路由器收到了明确的物理链路变化，重新创建 PPP 进程，执行 WAN、NAT、防火墙和策略路由脚本，最后记录 `WAN was restored`。网络随即恢复。

这不能百分之百排除运营商数据面异常，因为拔线也会迫使运营商释放并创建新的 PPPoE 会话；但结合两次恢复流程的差异，更值得优先怀疑的是，路由器在“PPPoE 内部重连”后没有完成整个 WAN 数据面的重建。

## 为什么路由器没有自动再拨一次

检查运行时 PPP 配置，可以看到：

```text
persist
holdoff 10
maxfail 0
```

这些参数表示，PPP 进程在明确发现会话终止后会持续重拨，失败次数不限，每次间隔约十秒。20:47 的日志也证明自动重拨确实工作过。

问题在于，“自动重拨”依赖于“先检测到断线”。当时的相关开关是：

```text
wan_ppp_echo=0
wandog_enable=0
dns_probe=0
```

PPP Echo、网络看门狗和 DNS 探测全部关闭。如果以太网载波仍然存在，PPP 进程也保留着接口和地址，但运营商不再转发数据，或者 NAT、路由和代理状态没有恢复，路由器未必会把它识别为一次 PPP 断线。应用层看到的是大量超时，PPP 层却没有收到足以触发 `persist` 的终止事件。

这也解释了为什么设备访问失败不一定留下 `DROP` 或 `REJECT`。互联网断开时，许多连接只是发出去后没有回应；而这台路由器的防火墙没有为每次丢包配置日志目标。现有计数器是累计值，没有时间戳，无法回溯到某一分钟的某台设备。

## 第一层修复：让 PPP 会话能够发现死亡

先启用固件原有的 PPP Echo，并保留原来的检测参数：

```text
wan_ppp_echo=1
wan_ppp_echo_interval=6
wan_ppp_echo_failure=10
```

应用配置并只重启 WAN 后，生成的 PPP 配置中出现了：

```text
lcp-echo-interval 6
lcp-echo-failure 10
lcp-echo-adaptive
```

它的含义是：PPP 会话在缺少有效流量时主动发送 LCP Echo，连续十次得不到回应后认为对端失效。按照当前间隔，理论检测时间约为一分钟。它解决的是 PPP 控制层的“假在线”，不会因为一次普通的公网 ICMP 丢包就重新拨号。

## 第二层修复：分层检测真实的互联网路径

LCP Echo 仍然不能覆盖所有故障。例如，PPP 对端会回应，但运营商公网路由不通；或者路由器自身能够访问公网，客户端路径上的 NAT、策略路由或代理却已经失效。因此，我又增加了一个每分钟运行一次的 WAN 健康监控器。

它按顺序检查：

1. WAN 网口是否有载波，以及协商速率和错误计数；
2. `ppp0` 是否存在公网地址和默认路由；
3. PPP 对端是否可达；
4. 两个不同运营商的公网探测地址是否至少有一个可达；
5. 使用当前上游 DNS 能否完成真实解析。

一次失败不会触发任何动作。只有同一种故障连续出现三次，监控器才会生成事故记录。这样可以过滤瞬时丢包、DNS 短暂超时，以及公网探测目标偶尔不响应等情况。

核心分类逻辑可以概括为：

```sh
if [ "$carrier" != 1 ]; then
    failure_class=physical-link-down
elif [ -z "$ppp_ip" ] || [ -z "$ppp_default" ]; then
    failure_class=pppoe-or-route-missing
elif both_public_targets_failed; then
    if ppp_peer_failed; then
        failure_class=pppoe-data-stale
    else
        failure_class=isp-upstream-unreachable
    fi
elif dns_lookup_failed; then
    failure_class=dns-failure
else
    failure_class=healthy
fi
```

分类本身比简单判断“网络通或不通”更重要。下一次再发生故障时，可以迅速判断证据停在哪一层：

| 现场状态                       | 优先判断                         |
| ------------------------------ | -------------------------------- |
| WAN `carrier=0`                | 网线、接口或上级设备的以太网链路 |
| `carrier=1`，没有 `ppp0`       | PPPoE 拨号或认证                 |
| `ppp0` 存在，PPP 对端不通      | PPP 会话假在线或运营商接入层     |
| PPP 对端通，两个公网目标都不通 | 运营商上游路由或数据面           |
| 公网 IP 通，DNS 失败           | DNS 服务或 UDP/TCP 53 路径       |
| 路由器自身正常，客户端异常     | NAT、防火墙、策略路由或 Xray     |

## 恢复之前先留下现场

监控器不会在发现异常后立即重新拨号。连续三次失败后，它会先把现场写入 JFFS：

- 时间、故障分类和连续失败次数；
- WAN 与 PPP 接口状态、速率及错误计数；
- PPP 地址、对端和进程；
- 全部路由与策略规则；
- DNS 配置和分层探测结果；
- NAT、filter、mangle 规则及计数；
- conntrack 数量；
- Xray、dnsmasq、wanduck 等关键进程；
- 最近三百条系统日志。

证据保存完成后，才执行恢复动作：

```sh
service "restart_wan_if 0"
```

这条命令只重建 WAN，不会重启整台路由器，也不会中断局域网管理面。DNS 单独失败时只重启 DNS 服务；物理网口掉线时只记录，不做无意义的软件重拨。恢复动作还设置了十分钟冷却时间，避免运营商长时间故障时形成重拨风暴。

监控器平时只把最新状态写入 `/tmp`，不会每分钟写入闪存。JFFS 只记录状态转换和事故快照；事故文件最多保留二十个，事件日志达到 1 MiB 后轮转。这样既能留下痕迹，也不会为了排障显著增加闪存磨损。

## 持久化与验证

监控脚本存放在 `/jffs/scripts/`，由 `services-start` 在启动时注册为每分钟运行一次的定时任务。部署前保留了原启动脚本，诊断目录使用仅管理员可读的权限，避免把局域网地址、路由和设备信息暴露给其他用户。

实施完成后，我做了四项验证：

1. PPP Echo 配置已经进入实际生成的 pppd 参数，而不只是停留在 NVRAM；
2. 只重启 WAN 后，PPPoE 获得新会话并恢复公网访问；
3. 完整的 `nat-start`、`wan-start` 和 `WAN was restored` 流程均出现在日志中；
4. 定时任务在下一分钟自动执行，PPP 对端、两个公网目标和 DNS 全部通过。

同时，我还保存了一份健康基线。下一次事故快照可以和它逐项比较，而不必再依赖“好像是光猫”“重启之后就好了”这样的模糊判断。

## 真正的目标不是自动重启

自动重启很容易制造一种虚假的稳定：故障很快消失，但原因永远不清楚。更可靠的家庭网络运维应该同时满足三个条件：检测必须覆盖真实的数据路径；恢复动作的范围应该尽量小；恢复之前必须保存现场。

这次改造没有直接启用一个只会重启整机的黑盒看门狗，而是让 PPP 自己识别失效会话，再由独立监控器区分物理链路、PPPoE、运营商出口、DNS 和客户端转发路径。以后即使故障自动恢复，也会留下足够的证据继续追查根本原因。

拔线仍然可以救急，但它不再是唯一的处理办法，也不再是排障的终点。
