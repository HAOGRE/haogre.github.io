家里有一个电视盒子，我想让它继续访问互联网和其他 App，但不能打开哔哩哔哩，也不能通过云视听小电视继续播放。限制范围要落在指定设备上，不能把整个家庭网络一起关掉。

这里的“屏蔽哔哩哔哩”不是让路由器对所有设备禁用哔哩哔哩，而是：家庭网络照常工作，只给选中的电视盒子、Apple TV 或 Android 盒子增加一条目标服务限制。其他设备不经过这条策略，目标设备上的其他 App 也尽量保持可用。

![小黑追着不断变化的 CDN 地址，静态 IP 黑名单总是慢一步](/uploads/2026/08/30/%E8%B7%AF%E7%94%B1%E5%99%A8%E6%8C%89%E8%AE%BE%E5%A4%87%E5%B1%8F%E8%94%BD%E5%93%94%E5%93%A9%E5%93%94%E5%93%A9%EF%BC%9A%E4%B8%BA%E4%BB%80%E4%B9%88%20IP%20%E9%BB%91%E5%90%8D%E5%8D%95%E4%B8%8D%E5%A4%9F/01-static-ip-pool.png)

_静态 IP 黑名单看起来直接，面对 CDN 的变化却很快变成追逐游戏。_

## 第一版为什么能用，后来却失效

第一版方案是让 dnsmasq 识别哔哩哔哩相关域名，把解析出来的地址放进一个集合，再用 iptables 只拦截指定 MAC 地址访问这些 IP。规则大概长这样：

```sh
ipset=/bilibili.com/bilibili.tv/bilivideo.com/bilivideo.cn/hdslb.com/biliapi.net/b23.tv/acg.tv/BILI_PROJECTOR
```

再配一条按设备匹配的转发规则，只有电视盒子的 MAC 命中时才拒绝连接。普通网页和其他设备不会被这条规则影响。

它一开始有效，是因为客户端当时恰好使用了黑名单里已有的地址；它后来失效，也不是 iptables 突然坏了，而是这套策略依赖了一个不断变化的中间结果：域名当前解析出了哪些 IP。

哔哩哔哩的域名很多，视频、图片、账号、配置和统计请求可能走不同的域名；云视听小电视还会使用自己的业务域名和 CDN。实际排查时，盒子的查询里出现过 `gtm.yst.aisee.tv`、`data.snm0516.aisee.tv` 和 `grpc.snm0516.aisee.tv`，它们并不属于最初列出的几组域名。

即使把当前解析到的 IP 都加进去，也有三个问题：

- IP 会过期，旧地址留在集合里没有意义；
- 新域名或新 CDN 会漏掉，客户端因此又能播放；
- CDN 地址可能被多个服务共享，粗暴地拦 IP 容易误伤其他 App。

所以问题不在于“还差几个 IP”，而在于用 IP 集合表达了一个本应由域名和客户端范围表达的业务策略。IP 适合做连接控制，不适合单独承担“这个设备不能访问某项服务”。

## DNS 过滤是入口，但不能单独承担全部拦截

后来引入了 AdGuard Home。它的作用不是自动接管整个家庭网络，而是给被选中的设备提供一个可以按客户端区分的 DNS 过滤层：目标设备的 DNS 请求被送到 AdGuard Home，其他设备继续使用原来的路由器 DNS。

![小黑在 DNS 分线台前拦截哔哩哔哩和云视听请求，让其他 App 继续通过](/uploads/2026/08/30/%E8%B7%AF%E7%94%B1%E5%99%A8%E6%8C%89%E8%AE%BE%E5%A4%87%E5%B1%8F%E8%94%BD%E5%93%94%E5%93%A9%E5%93%94%E5%93%A9%EF%BC%9A%E4%B8%BA%E4%BB%80%E4%B9%88%20IP%20%E9%BB%91%E5%90%8D%E5%8D%95%E4%B8%8D%E5%A4%9F/02-dns-filter.png)

_DNS 层能识别“要访问什么域名”，而且可以只对指定客户端启用规则。_

这层解决了静态 IP 黑名单最核心的问题：规则写的是服务域名，而不是一批几天后可能失效的地址。实际配置中，AdGuard Home 对目标客户端启用了内置的 Bilibili 服务规则，并补充了云视听实际使用的 `aisee.tv` 域名规则：

```text
||aisee.tv^
```

这条规则只对被选中的客户端启用，不是对全家启用。类似 `ptqy.gitv.tv` 这样的域名即使在日志里出现过，也不能仅凭一次观察就加入 Bilibili 黑名单，因为它可能属于共享的视频或电视基础设施；没有证据证明它是 Bilibili 专属域名，就不应该扩大拦截范围。

但是，DNS 也不是万能的。客户端可能使用缓存里的旧地址、直接使用硬编码 IP，或者尝试用 DNS-over-TLS（853 端口）绕过普通 DNS。于是最终方案没有停在“DNS 返回 0.0.0.0”，而是把 DNS 识别和目标设备的连接控制组合起来。

## 最终方案：按设备分流 DNS，再动态拦当前连接

现在的链路可以概括为：

```text
选中的电视盒子
  ├─ UDP/TCP 53 → 只转发给 AdGuard Home
  ├─ UDP/TCP 853 → 只对这台设备拒绝，避免绕过 DNS
  └─ 目标服务连接 → 按当前解析结果动态拦截

其他设备和目标盒子的其他 App → 继续走原有网络路径
```

具体分成四层：

1. **设备身份固定**：为目标设备保留固定 IP，并用 MAC 地址匹配它。以后增加设备，本质上就是增加一组 MAC/IP 映射。
2. **按设备转发 DNS**：路由器只把这台设备的 UDP/TCP 53 请求 DNAT 到 AdGuard Home 的专用端口。其他设备不经过这条转发规则。
3. **域名规则负责识别**：AdGuard Home 对这个客户端启用 Bilibili 服务规则和云视听业务域名规则；普通域名继续正常解析。
4. **动态连接规则兜底**：脚本定期解析配置中的服务域名，只保留当前解析到的地址，并重建目标设备专用的 iptables 链。旧地址被替换，不会无限追加到一张越来越大的 IP 表里。

![小黑把旧地址拿走，换上当前 CDN 地址；规则是替换，不是无限累积](/uploads/2026/08/30/%E8%B7%AF%E7%94%B1%E5%99%A8%E6%8C%89%E8%AE%BE%E5%A4%87%E5%B1%8F%E8%94%BD%E5%93%94%E5%93%A9%E5%93%94%E5%93%A9%EF%BC%9A%E4%B8%BA%E4%BB%80%E4%B9%88%20IP%20%E9%BB%91%E5%90%8D%E5%8D%95%E4%B8%8D%E5%A4%9F/03-dynamic-refresh.png)

_动态规则的重点不是收集所有历史 IP，而是只维护当前连接可能用到的地址。_

路由器上的实现文件分别承担不同职责：

```text
/jffs/configs/bili-projector-domains.conf  # 需要动态解析的域名后缀
/jffs/scripts/bili-projector-refresh       # 解析域名并重建当前连接规则
/jffs/scripts/firewall-start               # 开机时挂载按设备 DNS、853 和动态规则
```

当前域名配置覆盖了 `bilibili.com`、`bilibili.tv`、`bilivideo.com`、`bilivideo.cn`、`bilicdn1.com`、`hdslb.com`、`biliapi.net`、`b23.tv`、`acg.tv` 和 `aisee.tv` 等后缀。它不是声称“列完哔哩哔哩所有域名”，而是把已验证的业务入口交给 DNS 规则，再用动态连接规则处理这些域名当前解析出来的地址。

这里还有一个容易误解的名字：`BILI_PROJECTOR` 或 `BILI_PROJECTOR_IPS` 不是系统自带的魔法开关。它只是脚本创建的 iptables 链名，用来把“投影仪/盒子这台设备的 Bilibili 连接规则”集中起来。真正决定它做什么的是 `firewall-start` 和刷新脚本里的规则；复制一行时，应该复制完整的设备配置，而不是只写一个名字。

## 为什么只限制一台设备

按 MAC 匹配是整个方案的边界。它让规则只在目标设备发起连接时生效，因此手机、电脑和其他电视仍然可以正常访问网络。目标盒子本身也不需要被整体断网：只有匹配到 Bilibili 相关域名或当前目标地址的连接被处理，其他 App 继续走原来的出口。

![小黑只关上投影仪通往云视听的门，其他 App 和极米管理仍保持联网](/uploads/2026/08/30/%E8%B7%AF%E7%94%B1%E5%99%A8%E6%8C%89%E8%AE%BE%E5%A4%87%E5%B1%8F%E8%94%BD%E5%93%94%E5%93%A9%E5%93%94%E5%93%A9%EF%BC%9A%E4%B8%BA%E4%BB%80%E4%B9%88%20IP%20%E9%BB%91%E5%90%8D%E5%8D%95%E4%B8%8D%E5%A4%9F/04-device-isolation.png)

_限制策略的最小作用域是“某个设备 + 某项服务”，而不是整个局域网。_

增加另一台设备时，管理动作应该保持简单：

1. 给它做 DHCP 静态租约，确认 IP 和 MAC 不会变化；
2. 在 AdGuard Home 后台新增这个客户端，只给它启用 Bilibili 相关规则；
3. 在路由器的设备配置中增加一行 MAC/IP；
4. 重载防火墙或等待下一次动态刷新，再用该设备实际打开客户端验证。

删除设备时，反向删除 AdGuard Home 客户端和路由器里的那一行即可。不要只删除 DNS 规则而留下按 MAC 的动态连接规则，也不要只删脚本里的 IP；配置的来源应该始终是“设备身份 + 域名策略”，而不是手工维护一堆历史地址。

## AdGuard Home 在这里到底做什么

它在当前方案中的角色是“按客户端识别域名并执行 DNS 策略”，不是全家广告拦截器，也不是代理，更没有把 Xray 牵涉进来。Bilibili 的限制不依赖 Xray；路由器上可能存在其他用途的既有 Xray 配置，但这套 Bilibili 规则不把流量送进 Xray。

如果把全家设备的 DNS 都切换到 AdGuard Home，确实可以进一步做全网广告过滤，但那是另一个运维决策：规则量、误杀、日志和故障影响面都会扩大。当前选择按设备分流，是因为目标只是限制几个盒子，并尽量不改变其他设备的网络行为。

这种部署还有一个实际的可靠性好处：AdGuard Home 挂掉时，未被选中的设备仍然使用路由器原来的 DNS，家庭网络不会整体失去解析；代价是被选中的设备可能暂时无法正常解析域名。若要把它做成长期的家庭基础设施，应增加服务监控、配置备份和明确的恢复方式，而不是把所有设备无条件依赖在一个 DNS 实例上。

## 这套方案能解决到什么程度

它解决的是“指定设备按服务限制哔哩哔哩，同时保留其他 App 和其他设备网络”的问题：不依赖一份永远不会过期的 IP 清单，不需要把 Xray 牵涉进来，也不会因为某一次日志里出现一个共享域名就扩大到整个家庭网络。

它仍然有边界：如果客户端使用真正的硬编码 IP、通过 DNS-over-HTTPS 隐藏域名，或者把目标内容放在无法区分的共享 CDN 上，路由器很难做到既百分之百拦截又百分之百不误伤。动态解析和按设备连接控制可以把维护成本和影响范围压到合理程度，但不能把普通家庭路由器变成理解 App 内部协议的应用防火墙。

验证时不要只看“客户端能不能打开首页”，而要同时检查：AdGuard Home 查询日志中目标域名是否被拦截；动态链的计数是否增长；盒子的其他 App 是否仍能联网；手机和电脑是否没有被这条规则影响。只有四项都符合，才算达到了这个需求的真正目标。
